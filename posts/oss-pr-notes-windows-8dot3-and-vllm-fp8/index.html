复盘近期提交的两个公开开源 PR（agy-fast #101 与 vllm-metal #1431）的排错细节，以及四条实用的上游协作经验。

平时用开源工具遇到顺手能修的 bug，提个 PR 推回上游其实挺解压的——前提是别被跨平台 CI 杀个回马枪。

最近刚好连着提了两个风格完全不同的公开 PR：一个是 Node.js / TypeScript 写的插件工具（INK-Q/agy-fast #101），另一个是 Apple Silicon 上的推理后端（vllm-project/vllm-metal #1431）。两个问题都不算宏大，但踩出来的细节非常典型，趁记忆新鲜记下来。

一、Windows 8.3 短路径：realpathSync 和 promises.realpath 居然算出了两个哈希#

原本的 bug：多套安装目录互相覆写更新状态#

在折腾 agy-fast 的时候，同一台机器上经常会并存好几份安装——主目录一份 ~/.gemini，隔离环境里又通过 GEMINI_HOME 或者 --target 单独装一份。

原来的更新器逻辑（getUpdaterPaths()、readUpdateState()、writeUpdateState()）把 update-state.json 和锁文件 update.lock 全写死在同一个全局缓存目录 ~/.gemini/cache/agy-fast/ 里。结果就会串台：隔离环境那份刚升完级，把 lastCheckAt 和 notifiedAppliedVersion 写进了全局状态文件；主目录那份再启动时，读到“刚查过更新、也通知过了”，直接跳过检查，升级提示凭空消失。

修法很直白：保持 config.json 和环境变量 AGY_FAST_CACHE_DIR 原有语义不变，遇到非默认安装目录时，把规范化后的 pluginDir 算个哈希，把状态文件和锁文件隔离到 cacheDir/installs/<hash>/ 下；如果只是符号链接指向同一个主目录，经过 realpath 解析后依然共享主状态，不会无端分裂。

本地全绿，一上 Windows CI 红了#

改完后在 macOS 本地跑 npm run typecheck、npm run build 和 npm test（184 个用例）全部通过。推上 GitHub Actions 后，Ubuntu（Node 20/22/24）、macOS（Node 20/22/24）和 stress 7 项检查全绿，唯独 verify (windows-latest, Node 20) 挂了。

扒开失败日志一看，真是个经典的跨平台暗坑：

  • 在 GitHub Actions 的 Windows runner 上，os.tmpdir() 返回的路径带着 DOS 时代的 8.3 短路径名，类似 C:\Users\RUNNER~1\AppData\Local\Temp\...。
  • Node.js 里一对长得像双胞胎的同步/异步 API，在 Windows 上居然走了两套实现：
// 在 Windows runner 的临时目录下：
fs.realpathSync(dir);         // 纯 JS 实现：保留短路径 "C:\\Users\\RUNNER~1\\..."
await fs.promises.realpath(dir); // 调用原生系统 API：展开为 "C:\\Users\\runneradmin\\..."
fs.realpathSync.native(dir);  // 调用原生系统 API：同样展开为 "C:\\Users\\runneradmin\\..."

凑巧我改的两个模块里，src/utils/updater-core.ts 用了同步的 realpathSync，而 scripts/install.mjs 用了异步的 fs.promises.realpath。在 Linux 和 macOS 上两者输出一模一样，到了 Windows 上，同一个目录算出两个完全不同的字符串，哈希自然对不上，多安装隔离测试当场抓包。

修复只改了一行：把同步调用换成 fs.realpathSync.native，两边都走系统原生展开，推上去后 8/8 跨平台 CI 全部变绿。

✨ Node.js 跨平台缓存键小习惯

只要拿规范化路径当哈希输入、缓存目录名或锁文件标识，同步场景直接写 fs.realpathSync.native，和 fs.promises.realpath 保持同一套底层解析语义，能省掉在 Windows 上排查幽灵不一致的时间。

二、vLLM-Metal 块级 FP8 预检：写“提前报错”最怕漏拦和误杀#

第二个 PR 对应 vllm-project/vllm-metal 的 Issue #1410（PR #1431）。

在 Apple Silicon 上跑 vllm-metal 时，不少人会直接去 HuggingFace 拉现成的块级 FP8（block-FP8）checkpoint。这类权重在 config.json 里长这样：

{
  "model_type": "qwen3",
  "quantization_config": {
    "quant_method": "fp8",
    "weight_block_size": [128, 128]
  }
}

问题在于，mlx-lm 和 vllm_metal.compat 目前只给一部分架构实现了 weight_scale_inv 的块级反量化路径（比如 deepseek_v3 / kimi_k2、deepseek_v32、mimo_v2_flash、minimax / minimax_m2、mistral4、qwen3_5 / qwen3_5_moe）。像 qwen3、qwen3_moe、llama、ministral3、qwen3_next、glm4 这些架构，之前 EngineArgs.create_engine_config() 是直接放行的——用户得眼睁睁等几十 GB 权重拉完，或者加载到一半才炸出一个让人摸不着头脑的错。

看似一个 if，边界条件其实一串#

真顺着代码往里翻，发现写一个“靠谱的预检”远不止判断 weight_block_size 在不在：

  1. 模型类型名必须对齐 mlx-lm 的映射表：HuggingFace 的 model_type 和 architectures 有不少别名，不能只靠字符串硬写，需要把 mlx_lm.utils.MODEL_ARCHITECTURE_REMAPPING 和 MODEL_REMAPPING 同步进解析逻辑（resolve_mlx_lm_model_type）。
  2. 四类合法情况绝不能误杀：
    • 原生 MXFP8（scale_fmt="ue8m0" 且 weight_block_size=[32, 32]）是支持的，必须放行；
    • 不带 weight_block_size 的非块级 FP8 要放行；
    • 显式指定自定义 model_file 的情况要放行；
    • 还要确保不误伤 GGUF、mlx-vlm 原生多模态模型、STT 和 PyTorch MPS 路径。
  3. 拦截入口要覆盖完整：除了 MetalPlatform.check_and_update_config（同时查主模型和投机推理的 draft_model），还要把同样的预检挂到 ModelLifecycle 的文本模型加载入口和 draft_model_proposer._load_draft_model 上。只要命中不支持的块级 FP8，就在下载或加载权重前直接抛出项目已有的 UnsupportedQuantizationConfigError，明确提示换用 MLX 量化权重或 bf16。

最后写了 28 个覆盖各类配置组合的单测（test_fp8_reject.py），补上平台、生命周期和 draft proposer 的集成测试，本地跑通 ruff、mypy 和全仓 6,349 个非 slow 测试，签好 DCO 推上去。

✨ 写配置预检的检查清单

写“提前拒绝不支持配置”的补丁时，先列一张白名单边界表（原生变体、自定义入口、其他后端路径、辅模型/draft 入口），把每一种不该误杀的分支都写成单元测试，比事后被用户报回归省心太多。

三、四条提上游 PR 很管用的实在习惯#

对比小型工具库和 vllm-project 这种大型开源仓库，有四件小事做好了能省掉大半沟通成本：

  1. 写代码前先翻 CONTRIBUTING.md / AGENTS.md，顺手查重。大仓的流程往往写得很细，比如 DCO 签名（git commit -s），漏带一行 Signed-off-by 就会在 PR 检查里直接亮红灯；先搜一遍有没有现成的 Open PR 或已关讨论也能避免白忙。
  2. 先复现再落笔，别对着 Issue 猜路径。修 #1410 前，先本地跑了一遍 EngineArgs.create_engine_config() 确认 Qwen3 block-FP8 确实漏过，再顺着调用链把主模型和 draft_model 入口一次补齐。
  3. 复用项目现成的异常类和约定，克制重构欲。直接用仓库已有的 UnsupportedQuantizationConfigError，diff 只围绕这个 bug 展开，维护者扫一眼就能看明白，审核速度会快很多。
  4. 本机环境跑不了的检查，在 PR 正文里老实写明。这台 MacBook 上既没装 shellcheck，macOS SDK 版本（15.4）也达不到 vllm-metal 全量打包脚本要求的版本门槛。把**实际跑过的命令、精确通过数、以及哪两项受环境限制未跑（且未修改对应 .sh 文件）**原原本本列在 PR 描述里，远比含糊带过更让维护者放心。

平时写业务或跑实验遇到工具链的毛病挺烦的，但顺手把根因挖透、补齐测试、推回上游社区，再记成一篇短笔记，算是写代码里很有正反馈的一件事。
